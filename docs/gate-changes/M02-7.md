# Gate change M02-7: G5 started its healthz timer after port resolution, not at container start

- Gate: M02-G5 (the image works as a service)
- Files: `apps/fixture-hmi/scripts/gate-g5.ts`
- Raised by: independent review, round 2 ("G5 starts its healthz timer after port
  resolution, not at container start")

## Problem

The spec's pass condition is `/healthz` answering within 5s of start. `gate-g5.ts` took
`start = Date.now()` only after `resolveHostPort` had already returned — and
`resolveHostPort` itself polls `docker port` for up to 5s after `docker run` is spawned.
Whatever time port publication took was excluded from the measured window entirely, so
`healthyWithinMs` under-measured the real time from container start to a healthy
`/healthz`, by however long port publication took. Gate-change M02-4's note ("measured
from the same start point") was not accurate about this.

## Change

`start = Date.now()` now runs immediately before `docker run` is spawned, before
`resolveHostPort` is called at all. The healthz-polling loop's `while (Date.now() - start
< 5000 ...)` condition is unchanged in shape, but `start` now genuinely marks container
start, so the 5s budget covers port publication time too, matching the spec's window.

No threshold, count or coverage figure the spec states is touched — `healthyWithinMs` is
still bounded at 5000ms by `gates/M02.yaml`'s pass expression (unchanged); the fix only
corrects what instant the measurement is anchored to.

## Verified

`pnpm --filter @argus/fixture-hmi test:gate-g5` (via `pnpm gate M02`) passes:
`buildExit: 0, healthzOk: true, nonRoot: true`, with `healthyWithinMs` now including the
container's port-publication time.
