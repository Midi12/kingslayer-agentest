# Gate change M02-6: G4's half-period check bounded the mean, not each half-period, so it could not actually catch a wrong duty cycle

- Gate: M02-G4 (the blink is a real 1 Hz)
- Files: `apps/fixture-hmi/test/gate-g4.test.ts`, `gates/M02.yaml`
- Raised by: independent review, round 2 ("the G4 'duty-cycle' check added by gate-change
  3 cannot detect a wrong duty cycle")

## Problem

Gate-change M02-3 (round 1) added `meanHalfPeriodMs`, the *mean* of every gap between one
transition and the next, asserted to fall within 400-600ms, and claimed this would catch
"a wave whose half-periods are not ~500ms/~500ms ... regardless of what the full-period
mean reports". That claim does not hold: for any square wave of period P the half-periods
alternate `a`, `b` with `a + b = P`, so their mean is always ~P/2 regardless of how
lopsided `a` and `b` individually are. A 200/800ms duty cycle sampled for 5s (10
transitions, 9 gaps) gives a mean half-period of `(5*200 + 4*800) / 9 ≈ 467ms` — inside
the 400-600ms window the round-1 fix added. The mean check therefore still cannot tell a
200/800 wave from a correct 500/500 one; it happens to pass today only because the
current CSS implementation's duty cycle is in fact correct, so the gate would not catch a
regression here, and M02-3's own "Verified" claim about what the check does was wrong.

## Change

- `test/gate-g4.test.ts` now bounds every individual half-period to 400-600ms (not just
  their mean), and reports `halfPeriodsOutOfBand` (the count of half-periods outside that
  band) via `recordGateMetrics`. `meanHalfPeriodMs` is kept for observability but is no
  longer what the pass/fail decision rests on.
- `gates/M02.yaml`'s M02-G4 pass expression gains
  `metrics.halfPeriodsOutOfBand == 0 && metrics.distinctColors == 2` (previously enforced
  only through the test's own `expect` and the exit code, not through the yaml pass
  expression itself). `meanPeriodMs` bounds and `transitions >= 4` are unchanged.
- Also wrapped the browser/server/context lifecycle in `try`/`finally` (independent
  review, round 2, "gate suites leak browsers and servers when an assertion fails" — this
  suite's cleanup used to run only after every earlier `expect` had already passed).

No threshold, count or coverage figure the spec states is lowered — `meanPeriodMs` stays
900-1100ms and `transitions >= 4` is unchanged; two conditions are added, tightening what
already-collected data the gate acts on rather than relaxing anything.

## Verified

Wrote a standalone script simulating ~16.6ms-interval sampling (matching
`requestAnimationFrame` at 60fps) of a 200ms-on/800ms-off wave over a 5s window and ran
the same transition/half-period extraction the test uses: half-periods came out
`[797, 199, 797, 199, 797, 199, 797, 216]` — every one far outside 400-600ms — yet their
*mean* is 500.1ms, comfortably inside the 400-600ms band the round-1 (M02-3) check
bounded, and `halfPeriodsOutOfBand` is 8. The mean-only check would have passed this
wave; the per-half-period check fails it (`halfPeriodsOutOfBand !== 0`), as it should. A
correct 500/500 wave sampled the same way gives half-periods
`[498, 498, 498, 498, 498, 498, 498, 515]`, `halfPeriodsOutOfBand === 0`. Ran
`pnpm --filter @argus/fixture-hmi test:gate-g4` against the current implementation
(ADR-M02-2's CSS `steps(2, jump-none)` animation): passes, with every sampled
half-period within 400-600ms and `distinctColors === 2`.
