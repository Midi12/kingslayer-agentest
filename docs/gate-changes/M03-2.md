# Gate change M03-2: G3 plants key shapes below the generic thresholds

- Gate: M03-G3 (cassettes are strict)
- Files: `packages/testkit/test/m03-gate-g3.test.ts`
- Raised by: independent review, round 2 ("Key redaction misses unprefixed tokens under
  40 characters and lowercase-only runs; the independent G3 scanner has the same blind spot")

## Problem

G3 planted only keys that the generic rules already catch (prefixed keys, a mixed-case
base64 run of 40 or more characters, a long hex run). Its independent scanner also used a
40-character threshold for unprefixed runs, so a 39-character Google-style key in a query
string could reach a recorded file without either list noticing. A 42-character lower-case
token, and a 39-character run placed after a newline (40 characters once the file escapes
the newline as `\n`), were not planted at all, so their redaction was never exercised.

## Change

- Three more planted secrets in the recorded requests: a 39-character `AIza…` key in the
  query string, a 42-character lower-case alphanumeric token in the body, and a
  39-character mixed run after a newline in the body.
- The independent pattern list gains `\bAIza[\w-]{35}`. Its unprefixed-run rule already
  matches any 40-character run in the file text, escaped newline included.

The pass expression, every condition, threshold and count stay as they were; the change
only adds inputs and a pattern.

## Verified

With the redaction of the previous commit reverted to its round-1 behaviour (no Google or
lower-case rule, no check of the escaped form), the strengthened G3 fails: the files hold
9 planted secrets, 3 `keyPatternMatches` and 12 `independentMatches`. With the current
redaction G3 passes with no match of either list.
